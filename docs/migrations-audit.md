# Migrations audit (read-only)

Date: 2026-11-27. Scope: `supabase/migrations/*.sql` (001–221 on main; 222 is open in PR #143). `schema.sql` is stale and was used only to find base tables.
Method: the files were parsed statically by a script (tables, RLS, policies, FKs, indexes, guards), and every hit was checked by hand. **No database was queried**, so a finding means "the files say so". Whether a migration was actually pasted into prod can't be seen from the files.

Proposed fixes are **files only**, not applied:
- `supabase/migrations/223_storage_no_anon_listing.sql`
- `supabase/migrations/224_hot_lookup_indexes.sql`

## Ranked findings

| # | Severity | Finding | Fix |
|---|---|---|---|
| A1 | **High** | 9 public storage buckets still carry an unrestricted `FOR SELECT USING (bucket_id = …)` policy on `storage.objects`: `face-crops` (biometric face crops, 044), `program-plans` (coach PDFs, 016), `avatars`, `feed-media`, `store-products`, `badge-icons`, `perk-images`, `notification-images`, `event-images`. Migration 134 locked the `public` schema but left `storage` alone. With the anon key, which ships in the web bundle, anyone can **list** these buckets and enumerate every object. | 223 drops the 9 SELECT policies. Public URLs (`getPublicUrl`) keep working without them. The only `.list()` in the app is `run-chat`, which is server-side and service-role. |
| A2 | Medium (owner) | `face-crops` is a **public** bucket. Even with 223 applied, a crop URL works for anyone who has it, forever. This is biometric data. | Make the bucket private and serve crops through signed URLs from `/api/photos/*`. That is a code change too (`photos/process/route.ts` stores `getPublicUrl`), so it is not done here. Owner decision. |
| B1 | Info (verify) | 30 tables never get `ENABLE ROW LEVEL SECURITY` in their own migration (003–118: `role_tab_permissions`, `races`, `feedback`, `push_subscriptions`, `scheduled_notifications`, `athlete_faces`, `detected_faces`, `run_photos`, `client_events`, …). **All of them predate 134**, whose `DO` loop enables RLS on every `public` table and revokes anon/authenticated grants, including default privileges. Every table created after 134 enables RLS itself. So the files are clean **if 134 was applied**. | Run this in the SQL editor: `SELECT relname FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace WHERE nspname='public' AND relkind='r' AND NOT relrowsecurity;`. Expect 0 rows. |
| B2 | Low | Legacy `authenticated`-role policies (001 `"Coaches can manage own athlete activities"` with `coach_id = auth.uid()`, 017 weekly km snapshots) are dead: 134 revoked the grants they would need. They are harmless, but misleading to anyone reading the schema. | Optionally `DROP POLICY IF EXISTS` in a later cleanup. |
| C | Medium | Hot lookups with no matching index: `weekly_plans (athlete_id, week_start_date)` (about 68 call sites filter `week_start_date`; only `(athlete_id)` and `(coach_id, week_start_date)` exist) and `workout_deliveries (athlete_id, workout_date)` (about 29 call sites). About 60 FK columns have no index (list below). Most are on small tables, where that doesn't matter. | 224 adds the two composite indexes `CONCURRENTLY`. The FK list is left as is, since the tables are small (people-scale, not activity-scale). |
| D | Low | **Non-idempotent migrations.** These fail or duplicate data when re-pasted. **003, 007, 015**: `CREATE TABLE` without `IF NOT EXISTS`, plus seed `INSERT`s with no `ON CONFLICT`; re-running 007 would duplicate every `races` row. **016, 028, 001, 017**: `CREATE POLICY` with no `DROP POLICY IF EXISTS` or `pg_policies` guard, so a re-run errors. **083**: `ADD CONSTRAINT signup_requests_status_check` unguarded (089 later drops and re-adds it guarded). **211**: `ADD CONSTRAINT events_kind_check` follows a `DO` loop that drops it, so it is effectively guarded. All other `ADD CONSTRAINT`s are preceded by `DROP CONSTRAINT IF EXISTS`. | Historical files that have already been applied. Don't edit them; re-running them is never needed. Rule for new files (already in CLAUDE.md): `IF NOT EXISTS` / `ON CONFLICT DO NOTHING` / `DROP … IF EXISTS` first. |
| E | Info | **Duplicate REFERENCES (embed ambiguity).** 20 table pairs are joined by more than one FK, all listed in `schemaEmbedAmbiguity.test.ts` `KNOWN_AMBIGUOUS`. A scan of every `.from('<a>').select(…)` in `src/` for an unhinted embed of the other side of any of those 20 pairs found **0 hits**: every embed across an ambiguous pair is hinted (`!col`). | None. The test already gates new pairs. Migration 222 (PR #143) adds `email_log.campaign_id → email_campaigns`, which is its only FK to that table, so it is fine. |

## PII / credential / location columns

None of these are reachable without the service role once 134 is applied. They are listed here so any future policy that opens a table to `authenticated` gets reviewed against this list.

- **Location:** `athlete_activities` (start/end lat/lng, `gps_points`, `location_name`), `race_positions` (lat/lon, live tracking), `run_meetups` / `run_spots` (lat/lng, `area_lat/lng`), `events` / `races` (venue, not personal).
- **Contact:** `athletes` (`phone`, `birth_date`, `weight_kg`, email), `signup_requests` (email, phone, notify_email), `academy_candidates` (email, phone), `u21_registrations` (minors: `birth_date`, `guardian_phone`, phone, email), `store_orders.contact_phone`, `login_codes.email`, `login_handoffs.auth_email`, `feedback.athlete_email`, `email_log` recipients, and in 222 `email_events.recipient`.
- **Health:** `u21_registrations` (`flag_acute_injury`, `flag_bone_pain`, `flag_chest_pain`), `workout_feedback.pain*`, `academy_trainee_reports.pain*`, `athlete_wellness` (sleep, resting HR), `athlete_devices.health_authorized`.
- **Biometric:** `athlete_faces`, `detected_faces` (Rekognition face ids), plus the `face-crops` / `reference-faces` buckets (see A1/A2).
- **Secrets:** `athlete_claims.token`, `academy_candidates.invite_token`, `signup_requests.status_secret_hash` (hashed), `device_tokens.token_hash` (hashed), `athlete_devices.apns_token`. The two plaintext tokens (`athlete_claims.token`, `academy_candidates.invite_token`) could be stored hashed like the others. That is a follow-up and is not proposed here.
